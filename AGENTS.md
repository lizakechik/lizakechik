## О проекте
Это личный профессиональный сайт Елизаветы Кечик, продакт-менеджера.
Сайт нужен для:
- профессионального позиционирования;
- публикации продуктовых историй и кейсов;
- рассказа об опыте, образовании и профессиональном подходе.
Концепция сайта — личный сайт, построенный как книга с главами.
Основные разделы:
- Главная;
- Истории;
- Об авторе.
Сайт должен выглядеть как личное редакционное пространство, а не как типовое маркетинговое портфолио или сайт агентства.

## Позиционирование
Основная профессиональная роль — Product Manager / продакт-менеджер.
Дизайн, UX и аналитика — часть профессионального бэкграунда и перспективы, но не основное позиционирование.
В текстах и визуальной структуре важно показывать:
- продуктовый подход;
- понимание пользователей;
- бизнес-контекст;
- работу с ограничениями;
- взаимодействие с разработкой;
- понимание технологий;
- системное мышление.
Не использовать маркетинговые клише, преувеличенные заявления и пустые формулировки.
При редактуре сохранять авторский голос. Предпочтительны точечные правки, а не полная перепись текста.

## Визуальный стиль
Стиль сайта — спокойный, минималистичный, редакционный.
Основные шрифты:
- Source Serif 4 — заголовки и serif-акценты;
- Manrope — основной текст, подписи и интерфейсные элементы.
Не добавлять новые шрифты без явного запроса.
h1 используется только для главного Hero на главной странице.
На внутренних страницах максимальный уровень заголовка — h2.

## CSS
Структура CSS намеренно простая:
- global.css — глобальные переменные, типографика, базовые стили и общие utility-классы;
- крупные компоненты имеют собственные CSS-файлы.
Не усложнять архитектуру без необходимости.
Перед добавлением локального стиля проверять, не определено ли нужное значение уже в global.css.
Не дублировать в компонентных CSS глобальную типографику и цвета, если они уже определены в global.css.

## Layout и responsive
Использовать существующие контейнеры и паттерны ширины, а не создавать новые без необходимости.
При изменении компонента всегда учитывать мобильную версию.
Responsive — это не только уменьшение размеров: необходимо сохранять читаемость, иерархию и правильные расстояния между элементами.

## Истории
Продуктовые кейсы называются «Истории», а не «Проекты» или «Архив».
Список историй и отдельная история используют разные стили. При работе с отдельной историей не изменять стили списка без необходимости.
Не использовать h1 внутри содержимого истории.
Для Content Collections использовать существующую архитектуру проекта. Перед изменением src/content.config.ts сначала изучить текущую реализацию.
Не заменять существующий подход к Content Collections на другой без необходимости.

## Изображения
Не менять существующие источники изображений и asset paths без явного запроса.
Если изображение уже подключено через внешний CDN, не заменять CDN на локальный путь просто ради «упрощения».
Принцип внесения изменений
Перед изменением:
1. Посмотреть существующую реализацию компонента и его CSS.
2. Найти уже существующие глобальные стили и переиспользовать их.
3. Внести минимальное изменение, необходимое для задачи.
4. Не менять соседние компоненты без необходимости.
5. Не делать несвязанный рефакторинг.
6. Проверить desktop и mobile.
Не добавлять библиотеки, новые архитектурные уровни и абстракции без явной необходимости.
Если текущая реализация противоречит новой прямой задаче пользователя, приоритет имеет новая задача.

## Git
Не удалять, не откатывать и не перезаписывать несвязанные изменения пользователя.
Перед коммитом проверять git status и убедиться, что в коммит попадут нужные изменения.


## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.
